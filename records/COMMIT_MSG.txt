Unlock 75 GB of idle MIG capacity that the scheduler was refusing to use

The GPU inventory excluded MIG-enabled parents outright. The reasoning was that the parent
reports an aggregate free-memory figure yet is not schedulable as a whole device -- which
is true -- but the conclusion drawn from it was wrong: the MIG *instances* are perfectly
schedulable, and they were sitting idle.

Verified on this node before changing anything:

    CUDA_VISIBLE_DEVICES=6                        -> "MIG 1g.5gb", allocation succeeds
    CUDA_VISIBLE_DEVICES=MIG-10b9b777-...         -> "MIG 3g.20gb", 19.6 GB total,
                                                     11.0 GB free, allocation succeeds

The node has 7 x 1g.5gb on GPU 6 and 2 x 3g.20gb on GPU 7, i.e. about 75 GB of usable
memory that no job of ours could reach. Both scripts/gpu_util.sh and scripts/monitor.py
now enumerate instances by UUID (setting the parent index leaves it ambiguous which
instance you get, while the UUID is exact) and offer them to the dispatcher. Inventory
goes from 8 devices / 6 schedulable to 17 devices / 15 schedulable.

Per-instance free memory is derived from the profile name, because this driver does not
report it (`nvidia-smi -i MIG-<uuid>` returns "No devices were found"). That is a capacity
estimate rather than a measurement, so MIG targets still go through the OOM-retry path,
and the code says so where it matters.
