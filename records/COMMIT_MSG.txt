Corpus reality check: 2k tokens per sequence, so crop both ends; and stop writing to /tmp

Three fixes that only surfaced once the real corpus started flowing.

1. **The corpus is much longer than the official sample.** The official repository's
   sample FASTA averages 413 tokens per sequence; the real corpus averages 2,021, i.e.
   ~73 billion tokens in total. Plain head truncation at max_len 512 would therefore show
   only the start of every sequence and the 3'UTR would essentially never appear during
   pre-training -- silently disabling the 3'UTR half of the region objective, which is
   the thing this paper is about. The reader now crops from the head or the tail,
   chosen deterministically from the sequence index (so resuming and re-running with the
   same seed see identical crops). The main run moves to max_len 1024 with batch 4 x
   grad_accum 8, keeping the effective batch at 32 sequences per optimiser step.

2. **Worker temp files were being written to /tmp**, which on this node lives on the root
   filesystem shared with 68 other users: 440 files, 15 GB, on a partition with 103 GB
   free. They now go to the /mnt work directory (RNAJEPA_TMPDIR overrides), and the 440
   stray files were cleaned up.

3. **The first drain of results only happened after workers*4 batches**, i.e. after
   several million sequences, so pre.txt sat at zero bytes and the stage looked stalled
   for its first half hour. The window is now workers*2 and progress is logged every
   200k sequences.

Also: the machine has 96 cores and the first version asked for 96 workers, which
oversubscribed it alongside the reader and the GPU jobs; the run now uses 48.
