Learning-rate calibration: the official default fails on more tasks than first thought

The dev-set sweep over lr {1e-4, 5e-5, 1e-5} on the reference model, applied identically
to every model afterwards, changes four task settings and reveals that the collapse is
not confined to classification:

| task | 1e-4 | 5e-5 | 1e-5 | paper |
|---|---|---|---|---|
| cds_cov | 0.5382 | **0.8335** | 0.7869 | 0.89 |
| cds_riboswitch_1 | 0.3980 | 0.4193 | **0.5050** | 0.58 |
| full_in_cell_half_life | 0.4677 | **0.6688** | 0.4976 | (R2 0.769) |
| protein_solubility | **-0.0194** | **0.6488** | 0.6289 | (R2 0.63) |

protein_solubility at lr 1e-4 gives a Spearman of -0.019: a *regression* task collapsing
to no correlation at all, the same failure mode as 3UTR-RBP. cds_fungal is still worse,
-0.0041 against a published 0.89, and is now queued for its own sweep. So the documented
default is unsafe across task kinds, not just for classification with many samples.

The registry now carries lr_status: verified plus the measured evidence string for each
calibrated task, so the chosen value is traceable to a number rather than to taste. Cells
whose learning rate changed are re-queued with --force (the run overwrites its own output
directory, so there stays exactly one artefact per cell), and the five remaining
uncalibrated tasks are queued for sweeps.

Protocol integrity note: the sweep is run on the reference model only and the chosen value
is then applied to every model. Tuning each model separately would let the baseline and
the candidate end up with different hyper-parameters, which would make the head-to-head
meaningless.
