Fix a resumed pre-training run hanging forever instead of failing

Found while verifying resume with a small corpus: PHASE2 of the three-phase check sat at
zero output for over an hour. Two distinct defects, both in the data path:

1. Resuming with a corpus offset at or past the end of the corpus made the reader yield
   an empty iterator. The training loop then spun at zero steps per second, indefinitely
   -- no error, no progress, no log line. On the small verification corpus this triggered
   immediately; on the 36M-sequence corpus it would have triggered after one pass, i.e.
   potentially a day into the real run, and would have been very hard to attribute.
   Both readers now restart the pass from the beginning and say so, and
2. as defence in depth the loop now raises if an iterator produces no batches at all,
   so the failure mode is loud.

Also verified in the same session: a pre-training checkpoint written by this code loads
back into the model with missing=0 unexpected=0, so the released `bert.*`/`cls.*` key
layout round-trips correctly through save_hf_checkpoint.

Factor probe: the random-subspace control was vacuous and is now fixed. The K learned
blocks tile the hidden space, so concatenating all K is just an orthogonal rotation of
the whole vector -- and a linear probe is rotation-invariant, so the earlier control
reported numbers identical to the learned basis by construction (0.933 vs 0.933). The
control now fixes the *rank*: one random r_dim-dimensional subspace, probed exactly like
a single learned factor. A factor-specificity test is added alongside it, comparing each
factor against the union of the others, because that is the question C3 actually asks --
whether a factor carries privileged semantics rather than being one arbitrary partition
of a representation that is easy to decode from almost anywhere.
