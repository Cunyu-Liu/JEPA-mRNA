# 解码与速度审计：带状化无效、向量化 3–4×、以及必须收回的速度主张（2026-09-24）

> 起因：spec §5.0.1 把 System-1 定义为「单次前向 + **带状/近线性 DP**」，而评测驱动一直在用
> **精确 `nussinov_map`（O(L³) numpy）**。也就是说，此前所有延迟数字都是**精确解码**的数字，
> 不是所声称的 System-1 数字。补上 `--decode {exact,band}` 后做了实测。

## 1. 实测：带状化**几乎没有加速**

`eval/ss/evaluate_decision.py --decode exact|band --band 128`，TS0（1,288 条），batch 1，MIG 1g.5gb：

| 长度桶 | n | decode(exact) | decode(band=128) | total(exact) | total(band) |
|---|---|---|---|---|---|
| <100 | 565 | 44.8 ms | 46.4 ms | 113.8 ms | 112.1 ms |
| 100–200 | 528 | 134.7 ms | 138.7 ms | 232.5 ms | 230.1 ms |
| 200–400 | 167 | 639.4 ms | 659.2 ms | 953.7 ms | 954.0 ms |
| 400–600 | 28 | **1662.5 ms** | **1603.2 ms** | 2033.8 ms | 1942.7 ms |

**带状化在 400–600 桶只快 3.6%，在短桶甚至更慢。** 两个原因，都是结构性的：

1. **本实现的递推形式决定了带状的渐近收益本来就小。** 我们用的是「以 j 的配对者为轴」的递推
   （`N(i,j) = max(N(i,j-1), N(i+1,j), N(i+1,j-1)+s_ij, max_{k} …)`）。带状化把每个区间的候选
   `k` 限制到 `k ≥ j-band`，即每区间 ≤ band 个候选 → 总量 **O(L²·band/2)**，而精确是 **O(L³/6)**。
   L=500、band=128 时只有 **1.3×** 的运算量差。经典教科书里的 **O(L·band²)** 来自另一种递推形式
   （按 span 组织），本实现不是那种形式。
2. **真正的成本是 Python 层对 O(L²) 个区间的循环开销**，而带状化并不减少区间数。

> **结论**：在本递推形式下，"带状/近线性解码"这个说法**不成立**，必须从规范里改掉或明确标注为需要重构递推。

## 2. 向量化：3–4×，且**逐位等价**

把内层对 `i` 的循环整体向量化（对固定 span `d`，所有 `i` 相互独立）。令 `u = k-i-1`，三个 per-k 项
各自变成一次 fancy-index gather：

```
N[i, k-1]     -> N[i, i+u]            gather at (i, i+u)
N[k+1, j-1]   -> N[i+2+u, i+d-1]      gather at (i+2+u, i+d-1)
scores[k, j]  -> scores[i+1+u, i+d]   gather at (i+1+u, i+d)
```

Python 迭代数从 **O(L²) 降到 O(L)**。实测（同一台机器，参考实现 vs 快速实现）：

| L | 参考 | 快速 | 加速 |
|---|---|---|---|
| 100 | 64.3 ms | **16.2 ms** | 4.0× |
| 200 | 323.3 ms | **107.8 ms** | 3.0× |
| 300 | 1009.6 ms | **245.3 ms** | 4.1× |
| 500 | 1952.1 ms | **1055.5 ms** | 1.8× |

**等价性**：`tests/test_max_dp_fast.py` 25 项，对 `N`、`dec`、`kp` **三张表逐位相等**断言，
覆盖小长度（0–61）、`min_loop` ∈ {0,1,3,5,9}、任意（非 Watson-Crick）mask、大量并列值（tie）、
NaN/±inf 哨兵、全掩码。**必须比 `dec`/`kp` 而不只是 `N`**：tie 的破法不同会给出**同样最优但不同**的结构，
下游 F1 会无声漂移。参考实现保留在文件内（`_max_dp_reference`），`RN_FAST_MAX_DP=0` 可强制走它。
全量测试 **271 passed, 0 failed**。

L=500 时加速只有 1.8×，说明该规模下 **numpy 元素运算已超过 Python 开销**：每 span 的 gather 产生
`(n_k, n_i)` 索引网格，总计约 `L³/6 ≈ 2×10⁷` 次 fancy gather ×3，而 fancy indexing 比连续运算慢约一个量级。
进一步加速需要把 gather 换成**对角 strided 视图**（`as_strided`）或把 DP 编译（Cython/CUDA）。

## 3. 必须收回的速度主张（**重要**）

原先 spec §8.3 S1「相对 McCaskill 加速 ≥ 50×」、S3「L=512 延迟 ≤ 10 ms」**都不成立**：

- **决策头省掉的是「配分函数」，不是「DP」。** 校准通常必须算配分函数（O(L³) + 指数/对数运算，
  常数很大）；我们把它换成了 **1 次前向**（O(L²d)，GPU 并行）+ **1 次 max-product DP**
  （仍是最坏 O(L³)，带状 O(L²·band)）。所以**渐近意义上并没有省掉 DP**。
- **墙钟时间上我们更慢**：L≈500 时我们的 System-1 ≈ 1.2 s（解码）+ 0.37 s（前向），
  而 ViennaRNA 的 BPP 是 **C 代码**，量级在几十 ms。我们慢 20–50×，差距来自**实现语言**而非算法。
- **S3（≤10 ms）用本解码器不可能达到**，需要编译实现。

**正确的、可辩护的主张**（据此改写 spec）：

> **C1 的实质是「不必求配分函数就能给出校准概率」**——配分函数正是校准的传统代价。
> 我们用一个可学习打分 + 单次前向替代了它，并证明其概率可以被训练到与精确边际同等校准。
> **速度收益是常数因子级别（去掉指数/对数、GPU 并行、无 O(L³) 配分函数），不是渐近级别**，
> 且当前解码器是 Python 实现，墙钟上慢于 ViennaRNA，需编译实现才能兑现。

这条修正**不削弱 C1**（校准才是卖点），但**必须删掉一切"快 50×/10 ms"的表述**，否则审稿人一击即穿。

## 4. 顺带修正我自己此前的一条判断（finding C）

我在 spec §0.9.5 发现 C 里写过「`grad_clip=1.0` 而裁剪前范数 40–673 → **每步都被裁死**，有效步长波动」。
**这个推理是错的**，应当收回：

`clip_grad_norm_` 做的是**全局等比缩放**（所有参数乘同一常数 `c = max_norm/‖g‖`）。而 AdamW 的更新是
`θ ← θ − lr·m/(√v+ε)`，其中 `m ∝ c·g`、`v ∝ c²·g²`，故 `m/√v` **与 c 无关** → **等比裁剪对 AdamW 近似是空操作**。
残余效应只有：`c_t` 逐步变化给动量 EMA 引入噪声。

**因此 T-A4（长度归一 + 重标定 grad_clip）的紧迫性低**，可以降级为可选项；
损失值本身仍**不可跨步/跨臂比较**（这条成立，因为它是按配对数求和）。
